# 开发规约

本项目按里程碑和验收闸门推进。任何改动都应缩短从当前状态到“可完整玩一局”的距离。

## 开始工作前

1. 阅读 `README.md`、`docs/00_项目现状.md` 和 `docs/01_落地路线图.md`。
2. 明确本次只推进哪个闸门、验收条件是什么、哪些文件是事实来源。
3. 先检索现有实现和引用关系。能修现有权威入口时，不新增平行系统、第二份状态或临时替代品。
4. 若需求会改变产品方向、存档结构、主循环或大量资产，先暂停并确认；普通实现细节自行判断。

## 实施边界

- 一次只处理一个可验证问题。禁止顺手扩功能、跨系统改名或大范围“顺便重构”。
- `WaveManager` 是阶段编排入口，AI Director 不得另建阶段权威；长期状态不得继续塞进角色静态变量。
- 视觉资产、碰撞/导航、玩法数据分别承担自己的职责。不要用视觉网格补丁掩盖导航问题。
- 不恢复旧课程版的联机、Android 和十波竞赛目标，除非路线图被正式修改。
- 新脚本必须从脚本目录或 `.uproject` 推导路径，不写开发者用户名、Downloads 路径或固定盘符。
- 不提交 IDE/UE 缓存、日志、本地连接配置、凭据、构建产物或个人工作目录。

## 完成标准

改动必须同时满足：

- 目标行为已实现，而不只是代码存在。
- 相关构建、自动测试或审计已运行；无法运行时明确写出原因。
- 没有新增警告、绝对路径、重复事实源和未解释的临时文件。
- 更新最靠近事实的文档，不新建一份重复交接稿。
- 提交只包含同一意图的变更，并能单独回退。
